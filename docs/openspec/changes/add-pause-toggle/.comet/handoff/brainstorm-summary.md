## 已确认事实（来自 Open 阶段与用户选择，不再重议）

- 暂停键为 **P**；运行中按 P 暂停，暂停中再按 P 恢复
- 暂停期间**仅 P 生效**：方向键 / WASD 与空格在暂停期间一律被忽略
- 暂停提示采用**画布内覆盖层**，风格与现有结束覆盖层一致
- 范围：`game.js` + `index.html`；不新增交付文件、不引入依赖
- 非目标：自动暂停、暂停计时、暂停菜单、多级暂停；不改方向键 / WASD 的既有语义
- 用户已确认：**P 与空格都过滤 `event.repeat`**（按键自动重复不重复触发单次命令）

## 关键约束（来自现有代码，已在 Design 阶段实读确认）

- `game.js` 为单一 IIFE，无构建、无依赖，需在 `file://` 下直接可用
- `step()` 首行已经是「非 RUNNING 即返回」——暂停态天然被挡住，**无需新增推进判定**
- `loop()` 的时间累加只在 `status === RUNNING` 分支内；非运行分支执行 `accumulator = 0`
  —— 让暂停态落入该分支，即自动实现「恢复后不补偿连走」
- `onKeyDown()` 目前**没有** `event.repeat` 过滤；`KEY_DIRECTIONS` 映射表不含 `p`/`P`
- 方向键分支先 `preventDefault()` 再判断状态，因此暂停时方向键「被忽略但不滚动页面」
- 空格分支先 `preventDefault()`，再仅在结束态重开——因此暂停时空格天然被忽略
- `draw()` 目前仅在结束态绘制覆盖层
- 项目不引入测试框架（既有设计非目标），验证靠浏览器可观察行为与仓库外黑盒脚本

## 确认的技术方案

1. 状态机由两态扩为三态 `RUNNING | PAUSED | OVER`，状态常量集中定义
2. **不新增"是否推进"判断**：复用 `step()` 的既有守卫，并让暂停态落入 `loop()` 的 `accumulator = 0` 分支——这是"恢复后不补偿连走"的实现，也是本次唯一需要实测的高风险点
3. P 键作为 `onKeyDown` 中**独立分支**，位置在方向映射表查询之前（否则会因 `hasOwnProperty` 提前返回而永不生效）；只在运行/暂停两态间切换
4. 在 `onKeyDown` 入口统一过滤 `event.repeat`，对 P 与空格两个单次命令键生效
5. `draw()` 增加暂停覆盖层，与结束覆盖层互斥（`if OVER ... else if PAUSED ...`）
6. P 键无需 `preventDefault()`：浏览器对 P 无默认行为可抑制

## 关键取舍与风险

- [恢复瞬间补偿式连走] → 暂停态落入 loop 清零分支；已固化为独立 Scenario 并需实测
- [按住 P 反复切换暂停/恢复] → 统一过滤 `event.repeat`；否则长按 300–500ms 就会触发自动重复，表现为"按 P 没反应"
- [P 分支放错位置导致永不生效] → P 分支必须早于 `hasOwnProperty(KEY_DIRECTIONS, ...)` 的提前返回
- [结束态误响应 P] → P 分支只在运行/暂停两态切换
- [暂停覆盖层与结束覆盖层同时绘制] → 两态互斥，绘制二选一
- [既有 17 个 Scenario 回归] → 暂停不触碰方向校验、进食、碰撞；集成验收做全量回归
- [本 change 顺带修掉上一 change 的已接受偏差 D-3（按住空格重复重开）] → 用户已明确同意；需在 delta spec 中补对应场景
